# Assumptions

- **Runtime:** Python 3.11+ and SQLite are enough to run the assignment locally. PostgreSQL is supported by setting `DATABASE_URL`; schema constraints stay the same.
- **Identifiers:** Account, transaction, and transfer ids are UUID strings generated by the server.
- **Money:** Amounts use two decimal places. JSON responses serialize money as strings (`"100.00"`), not floats.
- **Initial balance:** Always `0`. Extra create-account fields (including `balance`) are ignored rather than rejected, so clients cannot set the opening balance.
- **Duplicate transactions:** HTTP `409` with the original transaction in `error.details.existing_transaction`. This is treated as the “already exists” response; the retry is not a second credit/debit.
- **Duplicate transfers:** `reference_id` is unique across all transfers. Ledger legs use `{reference_id}:debit` and `{reference_id}:credit` so each account still satisfies the per-account uniqueness rule.
- **Pagination:** `page` is 1-based. `limit` defaults to 20 and is capped at 100. `total_pages` is `0` when there are no matching rows.
- **Sorting:** Latest-first on `created_at`. `id` is a tie-breaker when timestamps match (for example both legs of a transfer).
- **Immutability:** No update/delete endpoints exist for transactions or transfers. Database rows are not rewritten after insert.
- **Atomicity:** Application code updates balance in the same unit of work as the transaction insert. Database checks (`amount > 0`, `balance >= 0`, unique `(account_id, reference_id)`) are a second line of defense.
- **Concurrency:** Account rows are locked with `SELECT ... FOR UPDATE` (SQLite still serializes writers). Transfer locks both accounts in sorted id order.
- **Auth:** Out of scope. The API is open locally.
- **Time:** `created_at` is UTC.
- **Names:** Account names are stored trimmed; blank names are invalid.
- **Unknown JSON fields:** Pydantic ignores extras on request bodies unless a field is explicitly modeled.
